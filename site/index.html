How it is built · the partner kit

What happens when you run /assess

The kit is custom SI configuration for vanilla IBM Bob, kept as plain files you can read and change. Here is one command followed through it, step by step, with the file behind each step.

  1. You type the command

    You type /assess and a run name. The command file says which mode and skill Bob uses, the three files he writes and the two checks you run afterwards. In any other mode it stops and asks you to switch.

    .bob/commands/assess.md

  2. The mode sets what Bob may do

    The command needs the architect persona, si-architect. It may write only the Discover and Assess files under runs/<name>/ and has no shell. It is told to use the read-only tickets tools only in /assess, and the read-only checks tool on its own files.

    .bob/custom_modes.yaml

  3. The rules load

    The shared rules apply in every mode: the goal, where Bob may work, how he cites evidence and when he stops. The architect's own rules add its scope, inputs, outputs and stop conditions.

    .bob/rules/ .bob/rules-si-architect/AGENTS.md

  4. The skill brings the method

    The si-assess skill holds the assessment contract, three templates (the assessment, the target annexes and the findings file) and the findings checker. Bob also reads the SI's report standard and scoring rubric.

    .bob/skills/si-assess/ .bob/standards/

  5. Bob reads the evidence

    He reads what /discover left in the run folder and the code metrics you produced with the metrics tool after it; Bob measures nothing himself. He opens the source only to confirm a line he cites.

    app/ tools/metrics/complexity_metrics.py

  6. He checks the ticket history

    He uses the read-only tickets tool, which serves synthetic data, and asks you before every call. A ticket can back up a finding from the code; it never proves one on its own.

    .bob/mcp.json tools/mcp/data/tickets.json

  7. The guard checks every step

    Before every tool call, the guard lets Bob read only inside the workspace and write only inside runs/<name>/. It refuses every shell command and every delete, move or rename, and it allows only the ten read-only tools of the four mock servers and the read-only checks tool. It is a backstop for mistakes, not a security sandbox, and it works only when Bob starts the kit's hooks, which he does only in a folder you trust. The repository's guide shows how to check, as its first step.

    .bob/settings.json .bob/hooks/pre_tool_guard.py README.md

  8. Bob writes three files and checks them

    runs/<name>/reports/assessment.md, runs/<name>/reports/target-annexes.md and runs/<name>/data/findings.json. Then he runs your two checks on them through the read-only checks tool, which writes nothing, and corrects only what they name, for at most three rounds. He stops and tells you whether his last check passed.

    tools/checkers/checks_server.py

  9. Your checks decide

    You still run the findings check and the report check yourself. When both pass, the stage is done; when either prints errors, you paste them back and Bob fixes only what they name.

    .bob/skills/si-assess/scripts/validate_findings.py .bob/skills/si-collate/scripts/validate_report_quality.py

/discover runs in the same architect mode; /plan and /price each have their own. All three take the same path, each with its own skill and checks. The kit's own guide lists every file: .bob/README.md

To see these files change what Bob does, watch What Bob reads: probes in most of these places, with Bob's real replies.
