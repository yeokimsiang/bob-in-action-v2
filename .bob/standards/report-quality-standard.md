# Migration assessment report quality standard

**Purpose.** Apply this standard to the synthetic legacy-app assessment and to every target annex. The deliverable is a decision-ready SI/client draft, not a certification, signed proposal, fixed price, or proof of a production migration. These controls draw on public migration-assessment reports and guidance. Institutional names identify sources only; do not imply SEI, GAO, NIST, CISA, AWS, or the U.S. government endorses IBM Bob or this work.

## Required pack and identity

Maintain **one consolidated assessment**, target-specific annexes, an editable **effort CSV model**, a **dependency-aware implementation plan**, a **nonbinding unpriced draft SOW**, and a **validation/provenance ledger**. Each file carries version, as-of date, preparer, review status, source revision, and explicit synthetic-demo status. The assessment opens with a recommendation, reason, decision needed, pilot boundary, blockers, and the evidence that could change the decision. Annexes add target-specific findings, options, test or feasibility scope, and unresolved decisions; they link to the consolidated finding IDs instead of making independent executive claims.

Separate artifacts by origin: the legacy source in `app/`, Bob-authored output under `runs/<name>/`, and checker output. Preserve Bob's original files, plus subsequent corrections as separately versioned artifacts. Never make evaluator material or held-out answers visible to Bob. Identical wording between reference and output is neither success nor proof of independence. Assess behavior, requirements coverage, traceability, and observed tests.

## Claim and evidence rules

Every material statement needs a stable finding or test ID and a ledger pointer to exact file/path, command output, run ID, timestamp, source revision, or documented stakeholder assertion. Mark the evidence class: source/config inspection, build/test, runtime, interview, inference, or unknown. Do not promote an inferred dependency, topology, usage pattern, business priority, or service level into a runtime fact. Mark missing telemetry, owner interviews, backup/DR results, real data volume, deployment access, and security scan as explicit gaps when unavailable. A claim of dead code needs checked call sites, routes, reflection/configuration, generated use, tests, and owner/runtime uncertainty; otherwise say “not referenced by inspected paths.”

Security findings distinguish code/config defects, dependency version matches, scanner results, affected component status, execute-path reachability, and actual exploitability. Record scan/test scope and the exact result. A CVE match is `under investigation` until affectedness and path conditions are evidenced; `not affected`, `fixed`, or `unreachable` each needs a recorded justification. No scan means “scan not performed,” never a clean score.

The consolidated assessment explicitly covers legacy code health: missing or misleading documentation, excessive coupling or “hairball” paths, dead-code **candidates**, duplication, testability gaps, error and data handling, obsolete dependencies, security defects, and operational fragility. Each category has evidence-linked findings or an explicit “not evidenced in supplied scope” gap. Describe business and operational consequences rather than substituting a generic quality label. A numeric debt score is optional and cannot replace the underlying findings.

The one Bob Java invoice-preview pilot must state its objective, modified boundary, legacy and target revisions, actual command/test result, before/after behavior, failures, and route rollback evidence if exercised. Mark each metric as **observed pilot actual** or **future forecast**. A successful build or preview does not prove end-to-end migration, performance, security, deployment, or operational readiness. Other target cases receive assessment and planning only unless separately authorized.

## Estimate, schedule, and contract controls

The effort CSV is the single numeric source of truth. A WBS row states task/deliverable ID, scoped quantity and unit, role, low/central/high effort, estimate method, evidence or comparable, uncertainty driver, included/excluded state, and link to plan/acceptance. Keep assessment effort, completed pilot effort, and later migration forecasts apart. Reconcile row, role, and scenario totals; record calculation method and revisions. Avoid percentage savings, productivity multipliers, probabilistic confidence labels, and currency amounts without supporting data. Monetary fields remain `not priced` unless an authorized rate card, currency, tax/expense treatment, and conversion are documented. Bobcoin spend is a separate actual usage ledger, not an SI price.

The plan reuses WBS IDs and names task owner role, predecessor, client input, effort, duration basis, exit evidence, milestone, assumption, and status. Show the critical dependency chain and distinguish work from elapsed time. Delay a prerequisite in review; downstream gates must respond. Until client calendars and environments are known, use relative windows or label dates illustrative. The plan's accepted work cannot exceed demonstrated pilot scope.

For stakeholder visibility, map delivery work to role responsibilities and sign-offs, Git branch/commit/PR checkpoints, ticket IDs, wiki or decision records, review gates and evidence locations. Synthetic Jira/Confluence-like records are labelled as simulations and cannot establish an authenticated approval. The PM owns traceability and cadence; developers, senior reviewers, tech lead and QA retain distinct implementation, review and verification responsibilities even when demo personas share one account.

The SOW remains marked `Draft—synthetic demonstration / nonbinding / unpriced`. It defines purpose, boundaries and exclusions, deliverables, responsibilities, client dependencies, objective inspection method, reviewer role, review window, correction cycle, and change-control trigger. Approval, signature, rate, legal terms, and acceptance status stay `pending` or `TBD` unless evidenced by an authorized human. The SOW's deliverable IDs, effort, schedule, and pilot criteria must reconcile to the other pack items.

## Minimum authoring contract

The six originals must be useful without reading agent prompts. `assessment.md` provides the decision, inspected estate, legacy health, architecture/dependencies, security state, options and limits. `target-annexes.md` covers all seven frozen migration profiles; every annex names impacted legacy components, alternatives, compatibility constraints, preserved behavior, feasibility evidence or not-run status, WBS/effort uncertainty, rollback boundary and client decisions. `implementation-plan.md` shows waves, team responsibilities, dependencies, gates and delivery controls. `sow.md` cross-references all six deliverables and every scoped WBS/deliverable ID. `validation-ledger.md` records every active Q and B rubric ID, including NR/open states. No released artifact contains unresolved `{{...}}` template fields.

Run the skill-owned completeness checker before review. It proves membership, required sections, seven-target coverage, rubric coverage and WBS/deliverable cross-links only. Independent reviewers still decide whether evidence supports claims, estimates are reasonable, risks are complete and the pack is fit for client/SI review.

## Adversarial gate

Apply [the machine-reviewable rubric](report-quality-rubric.json) to the **actual outputs**. A reviewer attempts to disprove the recommendation, find missing or circular evidence, challenge dead-code and CVE assertions, recompute money and hours, shift a prerequisite, test the pilot's stated behavior, inspect the separation of Bob output from evaluator material, and search for invented approvals or secrets. Log each material discrepancy with artifact version and evidence. Correct the source artifact, preserve its original, rerun affected checks, and record the new result. Release only when no blocking failure remains and the rubric's ordinal gates pass; an unrun check is `not reviewed`, never pass.
