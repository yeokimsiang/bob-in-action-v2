# Decision-ready assessment

This is custom SI assessment IP, not an IBM premium workflow. Bob authors the recommendation and prose from the legacy source in `app/` and the run's discovery evidence; evaluator-only material and held-out answers are never available.

1. Read the report standard and rubric in `.bob/standards/` and the [assessment contract](references/assessment-contract.md). Use [assessment.md](templates/assessment.md) and [target-annexes.md](templates/target-annexes.md) for the two report artifacts, written to `runs/<name>/reports/`.
2. Inspect each finding independently and write [findings.json](templates/findings.json) to `runs/<name>/data/findings.json` with stable findings/evidence IDs, legacy-health category, business/operational impact, severity rationale, remediation options and pending decision owner. Give every accepted evidence ID exactly one disposition: `mapped` to its complete nonempty final finding list, or explicit `deferred`/`accepted_risk` with owner and reason. A final closure scan must reject an empty `mapped` row; when no finding references the evidence, use `deferred` with a pending client owner and an evidence-specific reason. Put the same disposition rows in `assessment.md`; authenticated human evidence is required before `accepted_risk` can represent client acceptance. Explicitly cover documentation, coupling/hairball paths, dead-code candidates, duplication, testability, error/data handling, obsolete dependencies, security and operational fragility—or state the scoped evidence gap. Version-advisory matches remain `under_investigation` until affectedness and execution-path evidence support a stronger status.
   JSON `severity` is always one lowercase string from `critical`, `high`, `medium`, `low`, `informational`, `unknown`; never write a number. A Markdown ordinal must include the matching word beside the number.
3. **Checker (the user runs it; Bob has no shell):** after Bob writes, the user runs [validate_findings.py](scripts/validate_findings.py) with Python 3.11+ from the repository root:

   `python .bob/skills/si-assess/scripts/validate_findings.py --input runs/<name>/data/findings.json --run-id <name> --evidence-map runs/<name>/data/discovery-evidence.json`

   Stdout lists checked IDs, `semantic_review: pending` and a SHA-256/byte-count descriptor for the exact `findings.json` bytes parsed. Exit 0 validates references/categories; exit 2 prints JSON errors. With the evidence map, the validator also rejects a finding whose only evidence is ticket records (`mcp:tickets/...` pointers): tickets corroborate, never prove. The user may add `--normalize-evidence-closure`, which rewrites `findings.json` in place to mirror links Bob explicitly declared on one side of the redundant finding/disposition relation; it records each changed path and before/after hashes, cannot invent links or alter prose/finding attributes, and leaves genuine conflicts for rejection.
4. Three required sections are specified in the [assessment contract](references/assessment-contract.md#factory-v2-sections): technical debt scored on a stated rubric from the SI-measured `runs/<name>/inputs/complexity-metrics.json` and labelled "SI-measured, Bob-scored"; modernisation options scored on stated criteria, including business criticality, against all seven paths; and operational history from the tickets tools (`mcp__tickets__tickets_search`, `mcp__tickets__tickets_get`, `mcp__tickets__incidents_list`), cited only as corroboration beside primary `EV-` evidence. The security section states "source-reading review, no scanner". The user checks them with `python .bob/skills/si-collate/scripts/validate_report_quality.py --partial-stage assess --pack runs/<name>/reports`.
5. Lead `assessment.md` with recommendation, reason, pending decision, pilot boundary, blockers and reversal evidence. Annex all seven targets against the actual legacy architecture using the common options/compatibility/delivery contract; unexecuted feasibility stays unknown. No AI enhancement is in scope. Hand findings to PM/commercial in the [finding schema](../../schemas/finding.schema.json) and [handoff schema](../../schemas/handoff.schema.json), preserving forecast versus observed pilot facts.
